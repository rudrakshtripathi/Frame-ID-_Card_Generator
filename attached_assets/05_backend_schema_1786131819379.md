# Backend Schema — HH Goa 2026 Frame Generator

## 1. Design stance
This app is deliberately close to stateless: no accounts, no session, no login. The only server-side state needed is a record of each generated share image so the OG-tag share page can serve it. A full relational DB is overkill for MVP — object storage keyed by UUID, plus optional lightweight metadata, is enough. If usage analytics become a requirement later, a minimal KV/log table is added without disrupting this design.

## 2. Object storage layout (Vercel Blob / R2)

```
/generated/{shareId}.png        → the final composited image, public-read
```

- `shareId`: UUID v4, generated server-side on upload, never derived from user input.
- Content-Type enforced as `image/png` regardless of client claim (re-encode/validate server-side).
- Public read access (needed for X's crawler and for the download/share flow) — no signed URLs required since there's no sensitive data in these images beyond what the user chose to upload and already intends to share publicly.

## 3. Optional metadata store (only if you want basic usage visibility)
If you want to track volume for your own reporting (not required by the brief), use a single lightweight table — Vercel KV (Redis) or a single-table on Postgres/Supabase both work; below is the logical schema either way:

**Table: `shares`**
| Field | Type | Notes |
|---|---|---|
| `id` | UUID (PK) | same as blob key `shareId` |
| `created_at` | timestamp | for retention/expiry cleanup |
| `image_url` | text | public blob URL |
| `format` | enum(`pfp_frame`, `id_card`) | future-proofs for Format B without a schema change |
| `file_size_bytes` | int | for storage monitoring |
| `client_ip_hash` | text (hashed, not raw IP) | only for rate-limiting/abuse tracking, not identity — hash it, don't store raw IPs, to avoid unnecessary PII retention |

No user table, no auth table, no photo-original table (the original uploaded photo never needs to be persisted — it's composited client-side and discarded; only the final output is stored).

## 4. API endpoints

### `POST /api/upload`
- Purpose: receive the final composited PNG from the client and persist it for the share page.
- Request: multipart/form-data, single file field, max 10MB (post-compositing output is much smaller than a raw 25MB photo).
- Server-side validation: re-check MIME type (magic bytes, not just header), reject if not a valid PNG, reject if dimensions are absurd (>4000px either side — sanity cap).
- Response: `{ "id": "uuid", "url": "https://.../s/uuid" }`
- Rate limit: 20 requests/min per IP (basic abuse guard).

### `POST /api/convert-heic` (fallback only)
- Purpose: server-side HEIC→JPEG conversion when client-side `heic2any` fails.
- Request: multipart/form-data, single HEIC file, max 25MB.
- Response: JPEG binary or `{ error }`.
- This path should be rarely hit — instrument it (simple counter) so you know if it's actually needed or if client-side conversion is covering ~100% of cases.

### `GET /s/[id]` (server-rendered page, not a JSON API)
- Renders HTML with `og:image`, `og:title` pointing at `/generated/{id}.png`.
- If `id` not found: friendly 404 with CTA back to landing, not a raw error page.

## 5. Retention policy
- Auto-delete objects in `/generated/` after 30 days (cron/scheduled function, or bucket lifecycle rule if using R2/S3-compatible storage with native lifecycle rules — cheaper than a custom cron job).
- This bounds storage cost and avoids indefinitely hosting arbitrary user-uploaded content, which matters for both cost and basic data-hygiene practice even though nothing here is sensitive.

## 6. Format B (ID Card) forward-compatibility
If Format B gets built later, the only schema change needed is populating the `format` field and adding two request fields (`name`, `role`) to `/api/upload`'s request body, stored alongside the image or baked into the composited image itself (recommended: bake into the image client-side like Format A, keep backend untouched — text is just another compositing layer on canvas, not separate backend logic).
