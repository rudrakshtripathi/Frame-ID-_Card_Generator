# Web App Flow — HH Goa 2026 Frame Generator

## 1. Primary flow (happy path)

```
[Landing screen]
   │  user taps "Upload Photo"
   ▼
[Native file/camera picker opens]
   │  user selects a photo
   ▼
[Validating] -- checks: type, size --> fail? → [Inline error, stay on landing]
   │ pass
   ▼
[Processing] (HEIC convert if needed → composite on canvas)
   │  target: <3s
   ▼
[Result screen]
   ├─ shows composited frame preview (full size)
   ├─ "Download" button → saves PNG to device
   └─ "Share to X" button
          │
          ▼
   [Uploading generated image to backend] (spinner, <1s expected)
          │
          ▼
   [X compose window opens] (new tab / native X app if installed)
          — prefilled: caption text + #FrameInGoa + share link
          — link preview shows actual generated graphic (via OG tag)
```

## 2. Screen inventory
1. **Landing / Upload** — hero copy, single primary CTA ("Upload your photo"), brief on what they'll get, brand styling front and center so even this screen is "on brand."
2. **Processing** — lightweight in-place state change (not a full route), skeleton/blur of the frame with a subtle loading indicator. No full-page spinner-only screen; keep the frame visible so it doesn't feel like a dead loading page.
3. **Result** — large preview of final graphic, Download button, Share to X button, optional "Start over" / "Try another photo" link.
4. **Share page (`/s/[id]`)** — server-rendered, mostly for the X crawler; for a human visiting it directly, show the image plus a "Make your own" CTA back to landing. This doubles as a light viral loop.

## 3. Error / edge-case handling
| Case | Behavior |
|---|---|
| Unsupported file type (e.g. .webp, .gif, .pdf) | Inline error under upload button: "Please upload a JPG, PNG, or HEIC photo." No route change. |
| File > 25MB | Inline error: "That photo's too large — try one under 25MB." |
| HEIC client-side conversion fails | Silently retry via server fallback endpoint; only show an error if that also fails. |
| Compositing fails (corrupt image, canvas error) | Error state on result screen: "Something went wrong generating your frame — try again." + retry button, no dead end. |
| Upload-to-backend fails on Share tap | Download still works (it's already client-side complete); Share button shows "Couldn't prepare share link, try again" without blocking download. |
| User denies camera/file permission | Standard OS-level handling; no custom overlay needed. |
| Slow network on HEIC fallback | Show elapsed-time-aware message after ~4s ("Still working — large photos can take a moment") rather than looking frozen. |
| User navigates back after result | Landing state resets cleanly; no stale processing state left over (all state is in-memory/client, no session dependency, so a full reload always works — this is deliberate per PRD's "must work in one pass" and adds resilience for free). |

## 4. State model (client)
Single-page state machine, no routing between upload/processing/result (keeps it feeling instant and avoids full page reloads):
`idle → validating → processing → ready → (sharing) → shared`
with an `error` state reachable from `validating`, `processing`, and `sharing`, always with a way back to `idle`.

## 5. Mobile vs desktop
- Mobile (primary): file input triggers native picker with camera option (`<input type="file" accept="image/*" capture>` used carefully — avoid forcing camera-only, allow gallery too).
- Desktop (secondary): drag-and-drop zone in addition to click-to-browse, same downstream flow.
