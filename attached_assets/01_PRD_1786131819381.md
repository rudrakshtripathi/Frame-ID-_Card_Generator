# PRD — HH Goa 2026 Frame/ID Card Generator

## 1. Background
HH Goa 2026 is running a shortlisting task: build a web tool that takes an uploaded photo and returns a branded, shareable graphic in one pass, no login, fast. This PRD scopes the product being built to satisfy that brief and pass shortlisting.

## 2. Scoping decision (read this first)
The brief offers two formats and says "pick one (or build both)." **This build targets Format A — PFP Frame/Overlay — as the MVP.** Reasoning:
- Format A has one input (photo) and zero form validation surface. Format B needs name + role/stack fields, which adds input validation, text-fitting-in-a-badge layout problems, and more ways for the "on-brand, one-pass, fast" requirement to break.
- The evaluators are grading execution quality, not feature count. A flawless single-format tool beats a shaky dual-format tool.
- Architecture below keeps the compositing engine format-agnostic, so Format B is an additive feature (new template + form fields), not a rebuild, if there's time left.

**Decision needed from you:** confirm Format A-only is acceptable, or tell me to prioritize Format B or both. Defaulting to A-only unless told otherwise.

## 3. Goal
Ship a live, working tool where a user uploads a photo and gets a downloadable, on-brand HH Goa 2026 PFP frame in seconds, with a working "Share to X" flow that shows the actual image in the link preview.

## 4. Success metric (for this task)
Binary, judged by the reviewer doing exactly this: open link on phone → upload a real photo → get an image back in under ~3 seconds → download works → Share to X opens a tweet with caption + #FrameInGoa + a visible correct image preview, all without hitting a login wall. Any failure in that chain is a failed submission regardless of how good the design looks.

## 5. Target user
The reviewer/evaluator, first. Real attendees, second (post-shortlisting, for the actual event). Design and copy should assume a phone, a real (imperfect) photo, and zero patience.

## 6. In scope
- Photo upload: JPG, PNG, HEIC (iPhone default format)
- Client-side compositing of uploaded photo into a fixed HH Goa 2026 frame template
- Handling of arbitrary aspect ratios / off-center crops without requiring the user to pre-crop
- Download as a real image file (PNG)
- Share to X: prefilled caption + #FrameInGoa, with correct OG image preview on the shared link
- Mobile-first responsive UI
- No auth, no account, no gate before result is shown

## 7. Out of scope (for MVP)
- Format B (ID Card) — stretch goal, not blocking submission
- Multiple frame style choices / themes
- Photo editing tools (filters, manual crop/zoom UI) beyond automatic smart-fit
- Analytics dashboards, admin panel
- Native app

## 8. User stories
1. As a user, I open the link on my phone, upload a photo from my camera roll, and immediately see it inside the HH Goa frame — no waiting screen, no signup.
2. As a user, I download the result as an image I can set as my X profile picture.
3. As a user, I tap "Share to X" and a tweet opens pre-written with the hashtag and my image actually visible in the card, not a blank box.
4. As a user on a slow connection or with a large photo (e.g., 12MP iPhone HEIC), the tool still completes in a reasonable time and doesn't error out silently.

## 9. Functional requirements
- FR1: Accept .jpg, .jpeg, .png, .heic/.heic uploads up to 25MB.
- FR2: Convert HEIC to a browser-renderable format before processing.
- FR3: Auto-fit any uploaded photo (portrait, landscape, square) into a fixed circular/square frame slot using center-crop, without distortion.
- FR4: Composite the photo with the HH Goa 2026 frame asset client-side and render a preview within 3 seconds of upload on a typical mobile connection.
- FR5: Provide a "Download" action producing a single flattened PNG at a resolution suitable for X profile pictures (min 400x400) and for a sharp link-preview card.
- FR6: Provide a "Share to X" action that opens Twitter/X's web intent with prefilled text, hashtag, and a link to a generated share page whose Open Graph image tag points at the user's actual generated graphic.
- FR7: No login/signup step anywhere before the result is shown.
- FR8: Errors (unsupported file, oversized file, processing failure) must show a clear inline message, not a blank screen or silent failure.

## 10. Non-functional requirements
- Performance: upload-to-preview under 3 seconds on 4G for a 5–10MB photo.
- Mobile-first: primary breakpoint is a phone screen; desktop is secondary.
- Reliability: must work in one pass — no dependency on a second visit, cookie, or session to complete the flow.
- Branding: frame must be unmistakably event-specific, not a generic logo overlay — clear typography, color, and iconography tied to "HH Goa 2026."
- Accessibility: sufficient contrast, alt text on result image, keyboard-operable upload button.

## 11. Constraints
- Must be a live working link by submission deadline (per task's "What to submit").
- No backend image-processing bottleneck that breaks the "few seconds" requirement — compositing must happen client-side; backend is only used for share-page/OG generation and optional HEIC fallback.

## 12. Risks
- **HEIC decoding in-browser is unreliable across browsers.** Mitigation: client-side heic2any conversion with a server-side fallback endpoint if client conversion fails.
- **X link previews cache aggressively / require crawlable static OG tags**, which a pure client-rendered SPA cannot provide. Mitigation: dedicated server-rendered share page per generated image (see TRD).
- **Off-center or extreme aspect-ratio photos look bad in a fixed circular crop.** Mitigation: smart center-crop plus a manual reposition (drag-to-adjust) as a fast-follow if time allows; document as known limitation if not.
