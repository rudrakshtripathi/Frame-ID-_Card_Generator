# TRD — HH Goa 2026 Frame Generator

## 1. Architecture overview

```
[Browser]
  ├─ Upload photo (file input / camera)
  ├─ HEIC → JPEG conversion (client-side, WASM)
  ├─ Canvas compositing: photo + frame PNG → flattened output (client-side)
  ├─ Download (canvas.toBlob → a[download])
  └─ Share to X:
        ├─ POST generated image (blob) → /api/upload
        ├─ Backend stores image in object storage, returns share ID
        ├─ Browser opens X web intent → https://twitter.com/intent/tweet?text=...&url=<share-page-url>
        └─ Share page (server-rendered, /s/[id]) exposes <meta property="og:image"> pointing at stored image
              → X's crawler fetches this page when generating the link card
```

Core principle: **compositing is 100% client-side** (this is what makes it "instant" and keeps server cost near zero). The backend's only job is making the result crawlable by X's OG scraper, which cannot execute JS and therefore cannot see a client-only result.

## 2. Stack

| Layer | Choice | Why |
|---|---|---|
| Frontend framework | Next.js 14 (App Router), React | Need server-rendered pages for OG tags (share page) alongside a rich client app — Next.js gives both without two separate services |
| Image compositing | HTML5 Canvas API | Native, fast, no library weight, full control over crop/fit math |
| HEIC decoding | `heic2any` (client, WASM) | Runs entirely in-browser, avoids a server round trip for the common iPhone case |
| HEIC fallback | Server route using `sharp` (Vercel serverless) | Safety net if client decode fails on an older/unsupported browser |
| Hosting | Vercel | Zero-ops deploy, serverless functions for the two backend needs, generous free tier, fast global edge for the share pages |
| Object storage | Vercel Blob (or Cloudflare R2 if avoiding vendor lock-in) | Need a public URL per generated image immediately after creation, no server-side image processing needed at rest |
| Data store | None required for MVP — blob storage keyed by UUID is sufficient | Avoids a DB dependency entirely for a stateless, anonymous, single-pass flow. See backend schema doc if a lightweight KV log is added for basic usage counting. |
| Styling | Tailwind CSS | Fast to build a clean, on-brand mobile UI without custom CSS overhead |

## 3. Compositing logic (Format A — PFP frame)

1. Load uploaded image into an `<img>` / `ImageBitmap`.
2. Determine the frame's "photo slot" geometry (fixed for a given template, e.g., a circle of radius R centered at (cx, cy) inside a 1000×1000 canvas).
3. Compute a center-crop scale factor: `scale = max(slotWidth / imgWidth, slotHeight / imgHeight)` — this ensures the photo fully covers the slot regardless of source aspect ratio (portrait, landscape, square all handled identically).
4. Draw the photo onto an offscreen canvas at the computed scale, centered on the slot.
5. Clip to the slot shape (circle or rounded square, per design) using a canvas clipping path.
6. Draw the frame PNG (transparent center, opaque border/branding) on top, full canvas.
7. Flatten to a single canvas → export via `canvas.toBlob('image/png')`.

This keeps FR3 (any aspect ratio, no distortion) and FR4 (near-instant) satisfied without a manual crop UI for MVP. Manual reposition (drag before flatten) is a straightforward addition if time allows — same pipeline, just recompute step 4 on drag events before final flatten.

## 4. HEIC handling

- On file select, check MIME type / extension.
- If HEIC: run `heic2any` client-side to convert to JPEG blob, then feed into the same compositing pipeline as any other image.
- If client conversion throws (some Android/older Safari edge cases): fall back to POSTing the raw file to `/api/convert-heic`, a serverless function using `sharp`, which returns a JPEG. This is the only case that touches the server before the result is shown, and only as a fallback path.

## 5. Share flow detail

X's crawler does not execute JavaScript, so a client-only SPA cannot serve a dynamic `og:image` per share. Solution:
1. After compositing, browser uploads the final PNG blob to `POST /api/upload`.
2. Backend stores it in blob storage at a UUID-keyed path, returns `{ id }`.
3. Frontend constructs share URL: `https://<domain>/s/<id>`.
4. `/s/[id]` is a Next.js server component that renders minimal HTML with:
   - `<meta property="og:image" content="https://<domain>/blob/<id>.png">`
   - `<meta property="og:title" content="I'm in for HH Goa 2026 🚩">`
   - A redirect-or-display page so a human clicking the link also sees the image, not just crawlers.
5. Frontend opens: `https://twitter.com/intent/tweet?text=<encoded caption>&hashtags=FrameInGoa&url=<share-page-url>`.
6. X crawls the share-page URL, reads `og:image`, renders the card with the actual graphic.

Note: web intent's `url` param and image cards are the standard, reliable way to do this without needing X API write access or OAuth — no login wall is preserved.

## 6. Performance budget
- Upload → composited preview: target <1.5s compositing time (canvas ops are cheap; bottleneck is HEIC decode on large files, budget up to 2s for that case).
- Total upload-to-preview: <3s on 4G, per PRD.
- Share-page first byte: <300ms (Vercel edge, static-ish HTML).

## 7. Security / abuse considerations
- File size cap (25MB) enforced client-side and re-validated server-side on the upload endpoint (never trust client-side-only limits).
- MIME/type sniffing on the server upload endpoint, not just extension check, to reject disguised files.
- No PII stored — no accounts, no email capture. Uploaded/generated images are the only stored artifact; set a retention/expiry policy (e.g., auto-delete after 30–90 days) to avoid unbounded storage growth and to limit exposure if someone uploads something they shouldn't.
- Rate-limit `/api/upload` per IP to prevent storage abuse (basic serverless middleware, e.g., 20 req/min).

## 8. Deployment
- Single Vercel project, Next.js app + two API routes (`/api/upload`, `/api/convert-heic`).
- Environment: Blob storage token as env var, no other secrets needed.
- No database migration needed for MVP.
